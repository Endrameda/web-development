# Hooks

> A hook is a command, HTTP call, MCP tool call, prompt or subagent that Claude Code runs automatically at a lifecycle event (`PreToolUse`, `Stop`, `SessionStart`…), so a rule is enforced by code instead of hoped for in CLAUDE.md.

| ---- | ------- |

## When to reach for it

You can tell Claude in your CLAUDE.md to run Prettier after every file edit. Most of the time it will, but that is a model following advice, so sometimes it won't. A hook is run by Claude Code itself on the event, whatever the model decides, so the rule stops depending on the model remembering it. (Not literally "no exceptions": a hook that fails can fail open, see Gotchas.)

Common use cases include:
- Auto-formatting after file edits
- Logging all executed commands for compliance
- Blocking dangerous operations like modifying production files
- Sending yourself notifications when Claude finishes a task

## How

Hooks are configured in JSON settings files. `.claude/settings.json` is the project file you commit and share, `.claude/settings.local.json` is yours for one project (gitignored), and `~/.claude/settings.json` is yours across all projects. You pick an event, optionally set a matcher, and provide a handler, usually a command to run.

Here is a list of some of the events:
- **PreToolUse** — runs before a tool call
- **PostToolUse** — runs after a tool call completes
- **UserPromptSubmit** — runs when you submit a prompt, before Claude processes it
- **Stop** — runs when Claude finishes responding
- **Notification** — runs when Claude sends a notification

That is only part of the events. The full list is in the [hooks reference](https://code.claude.com/docs/en/hooks).

`/hooks` is only a read-only browser for the hooks you have configured. To add, edit or remove one, change the JSON in the settings file; edits are normally picked up automatically by the file watcher.

#### Blocking with PreToolUse

`PreToolUse` hooks can **block tool calls** before they execute. Your hook receives the tool name and input as JSON on stdin. The exit code determines the behavior:

- **Exit code 0** — proceed normally.
- **Exit code 2** — block the action. The stderr message gets fed back to Claude as feedback so it knows why it was blocked and can adjust.
- **Any other exit code** — a non-blocking error that gets shown to you but doesn't stop anything.

## Gotchas

- **Exit 1 does not block.** Only exit 2 (or a JSON `permissionDecision: "deny"` on stdout) stops the call. A guard script that does `exit 1` on a bad command shows a warning and lets the command run.
- **What exit 2 does depends on the event.** It blocks a `PreToolUse` call or a `UserPromptSubmit` prompt. On `PostToolUse` the tool already ran, so stderr only goes to Claude as feedback.
- **Hooks fail open by default.** A timed-out `PreToolUse` hook, or one whose script path doesn't exist or isn't executable, lets the call continue. Set `"onFailure": "block"` on a `command` or `http` hook to fail closed
- **Stdout must be only the JSON.** Extra output around the object (a shell profile that prints something, say) makes Claude Code read it as plain text or a parse error. On exit 0 Claude never sees stderr, and plain stdout becomes context only for a few events such as `UserPromptSubmit` and `SessionStart`.
- **`UserPromptSubmit` runs before every prompt.** Its default timeout is 30s, not 600s like most events. On timeout its output, including any added context, is discarded and the prompt goes through anyway.
- **A bare server name matches nothing.** `mcp__memory` matches no tool, `mcp__memory__.*` matches the whole server. A matcher made only of letters, digits, `_`, `-`, `|` and `,` is an exact match (`Edit|Write`), anything else is an unanchored JavaScript regex.
- **`if` is a filter, not a security boundary.** It only works on tool events (on `Stop` it never fires) and is best-effort for Bash. Use permissions for hard allow/deny rules.
- **Hooks merge, they don't override.** User, project, local and managed hooks all add up, identical handlers run once, and matching hooks run in parallel, so you can't rely on their order. `disableAllHooks` cannot turn off managed hooks.
- **Cloud sessions don't read your local `~/.claude/settings.json`.** A hook you only put there won't run in a cloud session. Put it in the project's `.claude/settings.json`.
- **A command hook is a shell command with your rights.** *(My take, not docs.)* Read a hook someone committed to `.claude/settings.json` like any other script from the repo before you trust the folder.
